> **TL;DR：** 我统计了一个同时包含 npm Package、Next.js 和 iOS App 的 AI 协作项目，排除规划与纯思考时间后，192.4 分钟的可归因执行时间里，**60.7%** 花在构建、类型检查、测试、CI 等反馈环节，直接修改代码只占 **24.0%**。AI 已经显著压缩了代码生成时间，但没有同步缩短“确认代码是否正确”的时间，因此开发瓶颈正在从写代码转向反馈回路。未来决定 AI 开发效率的，不只是模型能多快生成代码，而是基础设施能否让 Agent 更快、更稳定地获得可信结果。

前段时间一个 AI 协作小工具收尾。整理材料时突然想起之前听尤雨溪分享 VoidZero：为什么 AI 时代还要把 JavaScript 工具链从底层重新做一遍？当时感触不多，这次灵机一动把项目里的 npm Package、Next.js 应用和 iOS App 统计了一下，才发现了一些很有意思的现象。

为了尽量看清执行阶段的真实结构，我排除了无法直接归因到具体子项目的规划与纯思考时间，只保留修改代码、运行命令、构建、检查、测试、排查和 CI 等操作记录。三个技术栈合计产生了约 **192.4 分钟**的可归因执行时间，其中 116.8 分钟（**60.7%**）花在了获得反馈上；直接修改代码只有 46.2 分钟（**24.0%**）；剩余 29.4 分钟（**15.3%**）是阅读排查和其他自动化操作。

换句话说，在这次 AI 协作项目里，真正占据执行时间的已经不是“把代码写出来”，而是“确认写出来的代码到底对不对”。

一次完整的开发迭代，其实可以粗略写成：

```text
一次迭代时间 = 思考与生成 + 构建、检查与测试 + 观察结果并决定下一步
```

AI 显著压缩了第一部分。过去需要开发者花几十分钟编写的代码，现在模型可能几十秒就能完成；但代码生成以后，项目仍然要经过类型检查、编译、测试、依赖安装、包验证、集成验证和 CI，最后才能得到一个足够可信的结果。正如开发版本的阿姆达尔定律：当某一个环节被大幅加速，剩下没有被加速的部分就会迅速成为总耗时的主导项。AI 让写代码变快了，但并没有自动让“确认代码正确”也变快。

## 三个技术栈，同一个结果

npm Package 部分一共记录了 159.6 分钟，其中反馈基础设施占 96.4 分钟，也就是 **60.4%**；直接修改代码占 25.9%，其他执行工作占 13.7%。更值得注意的是，反馈时间并不只是 TypeScript 编译：质量与发布验证占了 72.8 分钟，测试占 13.7 分钟，Git 与 CI 占 7.2 分钟，构建和依赖准备反而只是很小的一部分。一个 npm 包真正交付之前，需要确认的不只是“代码能不能运行”，还包括包内容是否正确、发布产物是否完整、依赖是否安全、集成流程是否兼容，以及 CI 能否稳定通过。

![npm Package 可归因执行时间拆解：反馈基础设施占 60.4%，直接修改代码占 25.9%](/static/images/blog/ai-dev-bottleneck-is-feedback-loop/npm-package-breakdown.webp)

Next.js 应用的绝对时间更短，一共只有 19.0 分钟，但结构几乎没有变化：反馈基础设施仍然占 **59.5%**，直接修改代码只占 13.7%。其中类型检查与质量验证用了 4.0 分钟，`next build` 用了 3.7 分钟，Git 与 CI、测试和依赖准备合计又占去一部分时间。AI 可以快速生成一个页面、修改一个接口或者调整一段状态逻辑，但真正决定这一轮修改是否结束的，仍然是类型能否通过、生产构建是否成功、测试是否回归，以及运行后的真实行为是否符合预期。

![Next.js 应用可归因执行时间拆解：反馈基础设施占 59.5%，直接修改代码占 13.7%](/static/images/blog/ai-dev-bottleneck-is-feedback-loop/nextjs-app-breakdown.webp)

Swift / iOS App 的数据更加明显：13.8 分钟的执行时间里，反馈基础设施占 **65.9%**，是三个技术栈中最高的；直接修改代码只占 15.9%。单是 `xcodebuild build` 就用了 5.0 分钟，Swift 类型检查与校验用了 2.2 分钟，`xcodebuild test` 又用了 1.6 分钟。AI 写出 Swift 代码并不慢，但每一次修改都要重新进入 Xcode、SDK、模拟器、签名、编译和测试组成的环境中接受验证。

![Swift / iOS App 可归因执行时间拆解：反馈基础设施占 65.9%，直接修改代码占 15.9%](/static/images/blog/ai-dev-bottleneck-is-feedback-loop/swift-ios-breakdown.webp)

这组数据当然不能被当成行业 Benchmark：它来自一个项目，三个子项目的样本量也并不均衡，其中 npm Package 占据了大部分绝对时间。但真正值得注意的不是合计后的 60.7%，而是三个技术栈在独立统计后都得出了接近的结果——反馈基础设施分别占 **60.4%、59.5% 和 65.9%**。工具不同、语言不同、运行环境也不同，但 AI 写完代码之后，都要跨越一条比代码生成本身更长的验证链路。

## Token 消耗和开发耗时不是一回事

我一开始还想把 Token 消耗和执行时间放在同一张图里，后来发现这很容易产生误导。Token 衡量的是模型读取上下文、进行推理和生成内容的工作量，而墙钟时间衡量的是整个开发系统完成一次迭代需要多久。两者相关，却不是同一个指标。

模型生成一段代码可能消耗大量 Token，但只需要几十秒；一次 `npm test`、`next build` 或 `xcodebuild` 可能几乎不消耗 Token，却让整个 Agent 等待几分钟。缓存构建结果、缩短测试时间或者优化 CI，未必能让 Token 账单明显下降，却可以直接减少每一轮迭代的等待；反过来，压缩上下文或换用更便宜的模型可以降低 Token 成本，却不一定能让构建和测试快一秒。

因此，AI 开发至少存在两套需要分别观察的指标：一套是模型侧的 Token、推理成本和生成速度，另一套是系统侧从“修改完成”到“得到可信结果”的反馈延迟。只优化前者，会得到一个写代码很快、但大部分时间都在等待工具返回结果的 Agent。

## AI 时代的基础设施，就是开发主循环

过去我们经常把基础设施理解成开发流程外围的配套：业务代码负责创造价值，构建系统、测试平台、缓存、CI 和预览环境则是为了支持业务代码。但在 AI 协作开发中，这种边界正在发生变化。Agent 真正协作的对象不只是一组 Repository 里的文件，而是一个可以运行、观察、修改和验证的 Environment。模型生成代码只是向这个环境提交一次新的实验，只有当环境足够快地返回可信结果，Agent 才能开始下一轮行动。

因此，AI 时代的“敏捷基础设施”至少需要具备几个特点：构建可以增量执行并充分利用缓存，类型检查和测试足够快且稳定，错误信息具有明确的定位并且适合机器解析，本地与 CI 使用尽可能一致的命令和环境，依赖和运行条件可以复现，同时还要提供能够快速验证真实行为的集成测试、模拟器或预览环境。它们不是为了让工程流程看起来更规范，而是为了提高单位时间内可以完成的有效实验次数。

以前我们说，写代码就是生产力；但当代码生成正在变成相对廉价的输入，生产力更准确的衡量方式，可能是一个人或一个 Agent 在单位时间内能够提出多少修改、完成多少验证，并从真实结果中继续推进多少轮。

谁能把“改完代码”到“知道结果”的时间从分钟压缩到秒，谁就不只是在让开发者少等一会儿，也是在扩大整个 AI Agent 系统的实验吞吐量。

**AI 时代，基础设施不再只是成本中心，而是迭代速度的乘数。**
