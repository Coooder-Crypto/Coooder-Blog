AI Coding 真正改变的，也许不是写代码的速度，而是软件工程默认的协作对象。

过去，研发流程主要解决“人如何协作”：需求怎么传递、代码怎么 review、测试怎么执行、发布谁来拍板。现在，Agent 已经能在边界清晰的情况下完成跨文件修改、补测试、分析日志，甚至推进一段可复核的研发任务。问题不再只是“模型能不能写代码”，而是：**我们的工程系统，准备好让 Agent 参与生产了吗？**

这也是我理解的 AI-Native Engineering。它不是给工程师配一个更强的代码补全工具，而是把 repo、任务、测试、发布和责任边界，逐步改造成 Agent 能理解、能执行、也能被人类验证的系统。

## 代码变便宜之后，什么变贵了？

AI 把实现成本压低了。

过去一个需求要花三天，可能是因为要找代码、查文档、补接口、手写实现、自己验证。现在，如果任务边界足够清楚，半天内完成第一版实现和测试并不罕见。手写代码占比下降，工程师的时间被重新分配到方案判断、改动 review、测试验证和风险控制上。

这不是“人不再需要懂代码”。恰恰相反，代码生成变快之后，理解和验证会变得更贵。

AI 可以很快给出一段能跑的实现，却不天然知道它是否符合真实业务意图、是否破坏兼容性、是否覆盖了关键边界，或是否会在发布后制造一个难以追踪的问题。实现速度提升得越快，错误扩散和 review 压力也会一起提升。

所以研发的核心瓶颈正在迁移：从“谁能实现”，转向“谁能证明这次改动是正确的”。

工程师的角色也随之变化。我们仍然写代码，但越来越像方案评审者、质量负责人和风险准出者的结合体：让 Agent 承担更多实现动作，同时为目标、架构、质量和线上后果负责。

## 传统流程的问题：人一直在替系统打补丁

很多团队的研发流程其实并不完整，只是人类工程师足够擅长补洞。

需求没写全，人会根据会议记忆补齐；测试入口不清楚，人会问熟悉模块的同事；owner 没写，人会在群里找；发布风险没有列出来，经验丰富的人会凭直觉多看一眼。

这些能力在人类协作里很自然，却往往没有沉淀为工程系统的一部分。

Agent 进入执行链路后，问题会被放大。它不稳定地知道哪些约束是默认前提，不知道谁有最终决策权，也可能只跑最容易通过的测试。过去由人吸收的信息缺口，会变成执行失败、局部最优修改，或者把风险转嫁给 review 的成本。

可以把这件事理解为：**人不只是流程的执行者，也是流程的补丁。**

AI-Native Engineering 要做的，不是要求 Agent “更聪明一点”，而是把过去依赖人脑补齐的部分显性化：

- 任务要有目标、非目标、验收标准和关键上下文；
- 接口要有兼容性要求、调用影响面和 owner 边界；
- 测试要有标准命令、最低门槛和失败处理规则；
- 发布要有风险分级、回滚路径和人类审批点。

当这些东西不再散落在人脑、聊天记录和口口相传的经验里，Agent 才能真正成为工程系统中的可靠参与者。

## Harness 不是文档负担，而是 Agent 的工程底座

我更愿意把这套能力称为 Harness。它不是一份 `AGENTS.md`，也不是一套 prompt，而是一组让 Agent 能够理解、执行和被验证的工程约束。

至少可以分成三层：

| 层级 | 解决的问题 | 典型内容 |
| --- | --- | --- |
| Context Harness | Agent 如何理解系统 | 模块边界、任务背景、依赖关系、owner、高风险目录、上下文地图 |
| Execution Harness | Agent 如何稳定完成动作 | build、启动、测试、部署、日志与观测的标准入口 |
| Verification Harness | 如何证明结果可靠 | CI、测试门槛、review evidence、风险标签、权限边界、回滚与准出规则 |

没有 Context，Agent 只能根据局部代码猜测；没有 Execution，它只能停留在“我改了代码”；没有 Verification，代码会生成得更快，但正确性、责任和风险最终仍全压在人的身上。

这也是为什么 Harness 必须前置。先让 Agent 具备执行能力、再补验证，不是提效，而是在放大风险。正确的顺序应当是：**先找验证闭环，再放 Agent 进入闭环。**

## 人和 Agent 的分工，不是替代，而是重新排布

AI-Native Engineering 不是让 Agent 接管研发，而是让它进入研发流程中最适合被委派的部分。

Agent 适合做第一版执行和信息整理：梳理代码路径、暴露需求歧义、完成初版实现、补测试用例、归纳日志、生成变更摘要、发现潜在风险。

人仍然应该 review 并 own 最关键的部分：优先级、产品意图、架构取舍、测试策略、生产准出、回滚决策和最终责任。

可以把这套关系概括为三个动作：

- **Delegate**：把有明确边界、可验证结果的任务交给 Agent；
- **Review**：由人审阅方案、影响面、证据和风险；
- **Own**：由人承担优先级、质量和生产后果。

这个分工在 SRE 场景同样成立。Agent 可以把告警、变更、日志和依赖关系聚成一条时间线，提出可能的爆炸半径和恢复建议；但故障分级、回滚和最终根因判断，仍然必须留在人类责任边界内。

## 为什么第一步应该从一个 repo 开始

如果要落地，不必一开始就谈组织重构、全自动发布或所有 repo 的 Agent 化。

最适合的起点是一个真实 repo。它离执行现场最近，上下文相对集中，动作可以用代码和命令表达，结果可以通过测试、CI、PR 和回滚机制验证。

一个最小试点不需要复杂，关键是跑通 Context、Execution、Verification：

1. **补齐上下文**：写清 `AGENTS.md`、README、目录职责、模块 owner、高风险目录和禁止自动执行的动作。
2. **固化执行入口**：把 build、test、lint、启动、部署、日志和观测命令收敛成可重复运行的标准入口。
3. **建立验证证据**：要求任务或 PR 说明改动范围、验证命令、执行结果、风险标签、发布/回滚影响，以及需要谁来准出。

先让 Agent 在文档更新、测试补全、PR 初审、发布检查等低风险、高频、可验证的任务上稳定工作。不要急着自动 merge，不要让它直接做核心架构决策，也不要让它越过生产审批边界。

## 结语：工程系统该开始为 Agent 留位置了

AI-Native Engineering 的重点，不是某个 Agent 今天是否足够强，而是 Agent 已经开始进入研发执行链路，并且不会再退出去。

软件工程将因此发生一次长期演化：repo 不再只存代码，流程不再只服务于人，验证不再只是上线前的最后一道关卡。系统需要承载可复用上下文，Agent 执行可验证任务，人类专注于判断、取舍、风险和优先级。

不必现在就回答未来研发的终局是什么样。但一个更现实的问题已经摆在每个团队面前：

**你的工程系统，准备好让 Agent 进来了吗？**

答案不需要从一次宏大的改革开始。先从一个 repo 开始，把上下文、执行入口和验证闭环真正写进系统里。
